## 1. 现状与痛点

`data/ctr_baseline.json`（v3.0，CTR 基准 7 维：channel/audience/coupon/stage/scene/plan_type/owner）当前是**写死口径**：

```json
"APP Push": {
  "baseline_ctr": 0.05,
  ...
}
```

错误来源不一定准——可能业务口径是"点击/送达"、我们是"点击/触达成功"；可能是"按 plan 加权"、不是 record 求平均。**任何一处不一致，反哺的全套链路（signature 算误差 / calibrate_baseline 校基线 / L1 GBDT 训练标签）都建在沙上**。

---

## 2. 我的倾向（v0.1）

**主推定义**：

> **plan 加权 CTR = `sum(plan.clicks) / sum(plan.reach_success)`**
>
> - 分子 = 该 plan 内"合法点击"事件去重后的累计
> - 分母 = 该 plan 内"有效触达"（已发送且未失败）的累计
> - 跨 plan 聚合：用 **plan 加权平均**（不是 record 加权，也不是中位数）

### 2.1 为什么这样定

| 选择项 | 倾向 | 理由 |
|---|---|---|
| 聚合方式 | **plan 加权** | CLAUDE.md §9 已写"CTR 一律 plan 加权"；不被极端 plan 拉偏；已有 `rank_plans` 实现 |
| 触达口径 | **触达成功** | 现 `data_loader` 用此字段；不是"预计触达"（避免估算误差） |
| 点击口径 | **点击人次（去重人）** | 与历史数据列名 `点击` 保持一致；不去重 person 会按"疯狂点击党"拉高 |
| 时间窗口 | **无截断（plan 全周期）** | 单 plan 周期一般 ≤ 7 天，时间窗口影响小；截断规则有需要再单独条陈 |
| 最小样本 | **`min_reach ≥ 1000` 才进入聚合** | 小样本噪声大；与 `rank_plans` 现有默认一致 |
| Granularity | **按 7 维查表聚合**（不是按 record 直接散点） | 与 `baseline_lookup` 一致；反哺 L1 可重训成同样维度 |

### 2.2 拆 CTR 后的派生指标

- **点击率**（最常见，业务心智 = 上面的 plan 加权 CTR）
- **转化率**：点击→下单。如果业务关心，再加一个 `conversion_rate` 同口径派生
- **UV-CTR**：`unique_clickers / reach_unique_users`（去重人）—— 给"触达人群里多少人点了"另一种视角

主推先只算**点击率**这一个，派生指标等业务有需求再加。

## 3. 待业务/数据方对齐的取舍（6 选 1 不是开放问）

每条都是选择题——你勾 ABC，**我据此落实**。

### Q1 · 分子：哪个事件算"成功点击"？

- **A** 任意点击（含误触 / 重复点）
- **B** 去重后的点击人次（**主推**）
- **C** 仅"有效点击"（停留 ≥ N 秒）

### Q2 · 分母：哪个算"有效触达"？

- **A** 触达成功（发送系统报的送达数）—— **主推**（与现 data_loader 一致）
- **B** 实际展示数（客户端曝光埋点）
- **C** 触达成功扣除退订（**主推更深**——防无效样本）

### Q3 · 时间窗口

- **A** Plan 全周期不截断（**主推**）—— 适合 ≤7 天的 plan
- **B** T+1 截断（只算前 24 小时点击，避免后期转化拉偏）
- **C** T+7 截断

### Q4 · 跨渠道（多渠道 Plan）聚合

- **A** 不跨渠道聚合（**主推**）—— 渠道是 baseline 7 维之一，跨合就降维了
- **B** 渠道之间再加一层"全渠道均值"

### Q5 · 异常处理

- **A** 已知问题 Plan（重复发送 / 错误圈选人群）剔除（**主推**）—— 但需要业务 flag
- **B** 全保留，靠 `min_reach` 阈值过滤小样本

### Q6 · 反哺入口校验

业务确认前，**不接真实反馈数据**（仍按 Handoff §6.2 / §6.3 规则）。这条不需要选择题，**只是同步**——业务确认后再走 PagePhase 5 P1 feedback 上传。

## 7. 答疑（业务可能会问的）

**Q：为什么不直接用 record 加权求平均？**
A：小 plan 容易被大 plan 边缘化，按 plan 加权大 plan 不带偏。

**Q：为什么不用"UV-CTR"作主指标？**
A：UV-CTR 在跨计划比较有说服力，但 plan 内时 7 维聚合常见丢失 `unique_users` 字段（部分来源没有）。点击率是最低公分母，先稳住。

**Q：口径改了，老 baseline JSON 怎么处理？**
A：保留 v3.0 文件（不动），新建 v3.1 加 `definition` 字段。老业务方调取不影响，**新 baseline_lookup 默认加载 v3.1**。
